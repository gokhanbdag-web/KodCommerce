KodCommerce - Project Decisions (Source of Truth)
Last updated: 2026-11-22
Status: Confirmed requirements from conversation; further requirements to follow.

1. Product
- Build an e-commerce system.
- Implementation language: PHP.

2. Language and localization
- The source language of the application and its original translation strings must be English.
- Provide translations using GNU gettext .po and compiled .mo files, in a WordPress-like translation workflow.

3. Administration navigation
- On desktop, the admin navigation must be a vertical sidebar on the left.
- Navigation must be organized into groups.
- Clicking a parent menu item expands/collapses its submenu in accordion style.

4. UI framework and styling
- Use Bootstrap throughout the administration interface.
- Do not write external/custom CSS stylesheets.
- Provide a Theme Settings section that can dynamically change theme colors and Bootstrap styling choices.
- Theme customization must respect the Bootstrap-only styling requirement.

5. Change management
- Treat this file as the canonical record of decisions for future KodCommerce work.
- Consult it before planning or implementing changes.
- Append new confirmed decisions as the user provides them; do not silently change existing decisions.
- Do not interpret unmentioned details as confirmed requirements.

Open questions (not yet decided)
- PHP version, framework/architecture, database, Bootstrap version, supported locales, exact theme-setting mechanism, mobile navigation behavior, and full admin menu structure.

6. Page management and homepage selection
- Provide WordPress-like page management.
- Do not hardcode page content or a fixed homepage in application code.
- All pages, including the homepage, must be created and managed through the page management interface.
- Administrators select which managed page serves as the homepage, as in WordPress reading/homepage settings.

7. Visual page builder
- Provide a WPBakery-style visual page editor with a row > column > widget hierarchy.
- A plus (+) control adds a new row.
- Each row has a column-layout control at its upper-left corner to select the number/layout of columns.
- Each column has its own plus (+) control that opens the widget panel.
- Support text and image widgets, among other future widgets.
- Row width is configured when the row is added, independently of widget selection. Width/layout choices must include full-width, contained/container, and fluid behavior.
- Allow the arrangement/containment of columns within a row to be configured independently from the row's outer width.
- Row background settings can override global theme colors and support either a background color or a background image.
- Support edge-to-edge banner sections using a row background image with overlaid text widgets.
- Provide a simple/plain text widget.
- Provide a distinct styled banner text widget with editable fields: eyebrow (short overline), caption (headline), and description (multiline textarea).
- Allow the text widget's text color to be selected, including when placed over a background image.
- IMPORTANT: Width and background settings belong to the ROW, not to the widget selection dialog. Column layout belongs to the ROW's column control. Widget configuration belongs to the selected widget.
- All editor output must remain consistent with the Bootstrap-only / no external custom CSS requirement. Exact technical approach to dynamic per-row styling is not yet specified.

Pending details
- Exact set of widgets, responsive column controls, banner typography presets, background-image positioning, content persistence format, and precise interpretation of contained versus fluid column behavior are not yet defined.

8. E-commerce widgets
- The visual page builder must include e-commerce-specific widgets in addition to general content widgets.
- Explicitly requested examples: recently added products and favorites.
- The widget system must be extensible to additional commerce widgets as requirements are defined.
- The styled banner text widget can also be used for CTA (call-to-action) sections; its eyebrow, caption, and description fields remain as previously specified.
- The exact behavior of favorites (e.g., per-user wishlist vs featured favorites), product sorting, and further widget types are not yet specified.

9. Product merchandising widgets and admin product flag (clarification)
- The 'Favorites' widget displays products explicitly selected by administrators, NOT each customer's personal wishlist.
- The product create/edit screen must provide a control to mark or unmark a product as a favorite.
- The Favorites widget dynamically lists products marked as favorites by admins.
- Provide a 'Best Sellers' widget. The user described this as customer-based; precise aggregation, ranking criteria and scope remain to be defined. Do not conflate this with admin-selected favorites.
- Preserve the previously requested 'Recently Added Products' widget.

10. Admin menu grouping: Content Management
- The left-side vertical accordion admin menu must contain a parent group named 'Content Management' (source language English; localized in UI).
- WordPress-like page management and its visual page editor belong under this Content Management accordion group.
- The widget architecture must remain extensible: additional widgets can be introduced later as needs arise, without defining the full catalog now.
- Other Content Management submenu entries and other top-level menu groups have not yet been specified.

11. Content Management > Page Management screen
- Clicking the Content Management accordion parent reveals the Page Management submenu.
- Clicking Page Management opens a page listing all previously created pages.
- Each existing page must have Edit and Delete actions.
- Provide an Add New Page action that opens the new-page creation screen.
- The page list is the entry point to creating and maintaining pages; page content remains managed rather than hardcoded.
- Details such as delete confirmation, search, filters, pagination, and list columns have not yet been specified.

12. Content Management > Blog Management
- Add a Blog Management submenu entry under the Content Management accordion group, alongside Page Management.
- Opening Blog Management displays two navigation cards: Categories and Blog Posts.
- Clicking Categories opens a category management page showing existing categories and an Add New Category action.
- The new-category form must include: Category Image, Category Name, and Category Description.
- The details of blog post editing, and any additional category fields or actions, have not yet been specified; await further requirements.

13. Content Management > Blog Management: posts listing (terminology correction)
- IMPORTANT CORRECTION: The user means BLOG, not BLOCK. The admin section is Blog Management; its two cards are Categories and Blog Posts, not reusable layout blocks.
- Clicking the Blog Posts card opens a list of previously created blog posts, displayed together with their categories.
- The posts list must support category filtering and date filtering.
- Provide an Add New Blog Post button opening a WordPress-like blog post creation interface.
- Further fields and exact editor behavior are pending the user's continuation.

14. WordPress-like content management (overarching requirement)
- The user clarified that both Page Management and Blog Management under Content Management should closely replicate the familiar WordPress administration workflows.
- Treat WordPress-style page and post creation, editing, listing and management as the reference interaction model, while retaining all previously specified custom visual page builder and Bootstrap-only constraints.
- Blog means posts/articles, not layout blocks. Do not reintroduce 'Block Management' terminology.
- Exact WordPress feature parity is not assumed for features not yet discussed; clarify when implementation choices materially differ.

15. Blog editor exception (explicit clarification)
- Blog post creation and editing screens must NOT use the visual drag-and-drop page builder.
- The WPBakery-style row/column/widget editor is for Page Management, not Blog Management.
- Blog posts use a separate, conventional WordPress-like post editing workflow; the exact text editor implementation has not yet been specified.

16. Independent CMS architecture (confirmed)
- KodCommerce must be fully independent of WordPress at runtime and in its core architecture.
- Recreate WordPress-like CMS functionality and familiar administration workflows using original PHP implementation, not by renaming or bundling the WordPress core.
- The target includes WordPress-like page management, blog management, media management, user/role administration, PO/MO localization, and an extensible plugin/module architecture, subject to further feature specifications.
- E-commerce, orders, payments and marketplace integrations should be developed as modular KodCommerce components.
- Do not copy WordPress proprietary branding, artwork, or third-party assets; respect applicable open-source licenses if any external code is incorporated.
- Preserve the previously agreed Bootstrap-only styling constraint and custom page-builder requirements.
- This architectural decision supersedes any earlier suggestion to use WordPress as the underlying engine.

17. ARCHITECTURAL CORRECTION — WordPress source fork (latest decision, supersedes section 16)
- The user will upload the latest WordPress source version to GitHub.
- KodCommerce is to be developed by adapting/forking that actual WordPress source, not by independently reimplementing WordPress functionality from scratch.
- The goal is to transform the fork into a KodCommerce-branded, independently maintained product while PRESERVING WordPress's existing functional capabilities and avoiding regressions.
- WordPress update-service dependencies are to be replaced with KodCommerce-controlled update services, including a properly designed, secured and maintained update delivery mechanism.
- The user has not yet supplied/uploaded the source in this turn. Do not begin modifying code until the actual repository/version is identified and inspected.
- WordPress GPL license notices and attribution obligations must be retained where required; rebranding does not eliminate license duties. WordPress trademark usage must be evaluated separately.
- This section explicitly overrides section 16's instruction to avoid using WordPress source. The earlier requirements for CMS features, localization, page builder and Bootstrap-based administration remain in force unless subsequently revised.

18. Full technical rebranding requirement (explicit, latest)
- Cosmetic rebranding alone is unacceptable. The user requires all WordPress/WP identifiers visible in file/directory paths, URLs, API routes, database prefixes and technical naming to be replaced with KodCommerce-specific identifiers, including wp-admin, wp-content, wp-includes and wp_ where feasible.
- This is a deep source-level fork/refactor, not merely an admin theme or white-label plugin.
- Existing functionality must remain intact; assess and test plugin/theme compatibility and migration impact, including legacy identifiers that external integrations depend on. Do not promise zero regressions or undetectability to source-code auditors.
- Preserve legally required GPL copyright, attribution and license notices; these cannot be erased to conceal origin.
- Before any implementation, inspect the actual uploaded WordPress version and produce a dependency-aware migration plan and test strategy. The source has not yet been supplied in this turn.
